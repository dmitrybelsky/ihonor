# Дизайн: двусторонняя синхронизация заметок HONOR ↔ iCloud

Дата: 2026-06-06
Статус: утверждён (ожидает старта Phase 0)

## Цель

Двусторонняя синхронизация заметок между **HONOR Notes** (HONOR Cloud / Data Sync)
и **iCloud Notes** (Apple ID). Запуск на **headless cloud-сервере** (без Mac в петле).

## Ключевые ограничения и принятые риски

Оба источника **без публичного API**. Решения приняты осознанно:

- **iCloud Notes:** надёжного headless API нет. AppleScript/`macnotesapp` требует Mac —
  отвергнуто. IMAP-заметки мертвы с El Capitan. Путь = reverse-engineering приватного
  web-API `icloud.com/notes`. Хрупко, ломается при изменениях Apple, требует управления
  2FA/trust-token. **Риск принят.**
- **HONOR Notes:** публичного web-notepad не подтверждено. Синхронизация идёт через
  HONOR Data Sync (HONOR ID) либо локальное хранилище Windows-клиента HONOR Notes.
  Конкретный механизм определяет **Phase 0 spike**.
- **Двусторонний режим** → нужны устойчивый mapping ID между системами и разрешение
  конфликтов (см. §4).

## Архитектура

Пять модулей, каждый с одной задачей. Sync-engine работает только через общий
интерфейс `NoteAdapter` — не знает деталей HTTP/протокола ни одной из сторон.

```
            ┌─────────────────────────────────────┐
            │            sync-engine               │
            │  reconcile + разрешение конфликтов   │
            └───────▲───────────────────▲──────────┘
                    │   NoteAdapter API  │
        ┌───────────┴──────┐   ┌─────────┴───────────┐
        │  honor-adapter   │   │   icloud-adapter    │
        │ (Data Sync,      │   │ (reverse iCloud     │
        │  уточняет Phase0)│   │  Notes web API)     │
        └───────────┬──────┘   └─────────┬───────────┘
                    │                     │
              HONOR Cloud           iCloud (Apple ID)
                    │                     │
            ┌───────┴─────────────────────┴────────┐
            │   state-store (SQLite)               │
            │  id-map · хеши контента · tombstones  │
            └──────────────────────────────────────┘
                    ▲
            ┌───────┴────────┐
            │   scheduler    │  poll-цикл (webhooks отсутствуют)
            └────────────────┘
```

### Интерфейс NoteAdapter (обе стороны реализуют одинаково)

- `list_changes(since_cursor)` → список изменений с курсором
- `get(id)` → `Note`
- `create(note)` → `ext_id`
- `update(id, note)`
- `delete(id)`

Канонический тип: `Note { ext_id, title, body, mtime, hash }`.

Sync-engine не трогает HTTP/протокол — только интерфейс. Spike может менять внутренности
honor-adapter (Data Sync API ↔ DB Windows-клиента) без правок движка.

Модель **poll-based** (не event-based): ни один вендор не даёт webhooks, scheduler
опрашивает обе стороны по интервалу и сравнивает со state-store.

## §2. Phase 0 — спайк (гейт)

Два неизвестных. До любого кода синхронизации доказать **чтение И запись** headless.

- **iCloud spike:** auth (Apple ID + 2FA → сохранить trust-token / cookies сессии),
  обращение к приватным endpoints `icloud.com/notes`. Доказать 5 операций: list, get,
  create, update, delete. Старт от auth/сессии `pyicloud`, заметки — на сыром `httpx`
  (собственная поддержка notes в pyicloud мертва).
- **HONOR spike:** перехват трафика HONOR Data Sync (HONOR ID login → notes endpoint)
  ЛИБО разбор локального хранилища Windows-клиента HONOR Notes. Доказать те же 5 операций.
  Какой путь рабочий — решает спайк.

**Гейт выхода:** обе стороны демонстрируют все 5 операций headless. Если любая
проваливается → стоп, пересмотр подхода (Mac-in-loop или смена Apple-таргета). Движка
синхронизации до прохождения гейта нет.

## §3. Синхронизация и конфликты

- Строка в state-store на пару заметок: `{honor_id, icloud_id, last_hash,
  last_synced_at, tombstone}`.
- Каждый poll: `list_changes` с обеих сторон → классификация каждой заметки:
  new / changed-one-side / changed-both / deleted.
- **changed-one-side** → push в другую систему.
- **changed-both (истинный конфликт)** → **conflict-copy**, не last-writer-wins.
  Межсистемные timestamps недостоверны; данные молча не теряем. Сохраняем обе версии,
  одну помечаем `(conflict YYYY-MM-DD)`.
- **Удаления — консервативно:** удаление пробрасывается, только если заметка была в
  id-map И подтверждённо исчезла — никогда по факту «не увидели при первом проходе».
  Защита от массового стирания из-за сбойной выборки.

## §4. Точность переноса (fidelity)

iCloud и HONOR обе богатые (картинки, чек-листы, рукопись, аудио). Кросс-синк лоссовый.

**Дефолтный объём: простой текст + базовое форматирование + встроенные картинки.**
Рукопись / аудио / сканы = best-effort либо пропуск с логом. Регулируется.

## §5. Безопасность (реальная экспозиция выбранной архитектуры)

Сервер хранит **креды Apple ID + 2FA trust-token + креды HONOR ID**. Компрометация
сервера = полный захват обоих аккаунтов. Меры в спеке:

- Секреты в env / secret-manager, **никогда** в репозитории, никогда в открытом виде на диске.
- Trust-token шифруется at-rest (ключ из env, не лежит рядом с данными).
- Выделенный сервер, закрытый доступ, в идеале без соседей-тенантов.
- Остаточный риск принят — он присущ выбору headless-сервера.

## Стек

Python · `httpx` · SQLite · launchd/systemd timer для poll-цикла.

## Порядок реализации

1. **Phase 0 — спайк** (гейт): доказать 5 операций headless с обеих сторон.
2. NoteAdapter + два адаптера (по результатам спайка).
3. state-store (SQLite) + id-map.
4. sync-engine: классификация + push + conflict-copy + консервативные удаления.
5. scheduler (poll-цикл) + запуск под systemd/launchd.
6. Безопасность: шифрование секретов, хранение trust-token.
